# 电商客服微调数据集 v1

## 用途与范围

根据用户指定的《项目实战(1).md》第四章制作。原文没有单独的电商微调小节，本数据选择 **4.3 客服项目模型微调**，将其应用于电商订单、售后、商品和优惠场景。不是4.2的SQL数据，也不是2.3的电商风控数据。

这是用于成熟大模型监督微调（SFT）的中文合成起步集，不包含模型权重或训练结果。全部订单、收件点、商品参数、金额、物流节点和规则均为虚构；商品材质及券规则仅对各条样例的上下文有效。

**180条样本，36个独立编写的场景族，每族5条参数化扩充。** 同族主要变化为商品名、订单号、金额和提问前缀，不应视为180个独立业务情境。真实业务训练前应补充经授权、脱敏、人工审定的历史会话，按实际业务规则复核标签；本集适合先验证数据读取、训练流程和初步效果。

## 文件

| 文件 | 内容 |
| --- | --- |
| train.jsonl | 120条训练样本，messages格式，一行一个JSON对象 |
| validation.jsonl | 30条验证样本，用于训练期间选模型及参数 |
| test.jsonl | 30条测试样本，确定方案后再做最终评估 |
| train_alpaca.json / validation_alpaca.json / test_alpaca.json | 相同样本的Alpaca格式，JSON数组，包含system和history |
| dataset_info.json | Alpaca数据注册映射；按所用训练工具版本核对后使用 |
| annotations.jsonl | 场景、集合、标签、样本ID和对应JSONL行号；不要直接当训练文件 |
| preview.json | 每个集合各2条完整样例，方便阅读 |
| stats.json | 数量、类别分布与数据局限 |
| validation_report.json | 验证脚本生成的检查结果及文件哈希 |
| build_dataset.py | 无第三方依赖的可复现数据构建脚本 |
| validate_dataset.py | 格式、隔离、转换及关键流程边界校验 |

两个训练格式内容相同，**二选一，不要合并后重复训练**。JSONL没有额外元数据字段，以减少数据加载配置差异；标签索引用annotations.jsonl追溯。UTF-8无BOM。

## 能力覆盖

每类30条，训练/验证/测试分别20/5/5：

- 订单物流：明确订单、缺订单、多轮补充、已知物流、多个候选订单、签收争议。
- 订单修改：缺地址、完整改址、取消确认、已发货改址、用户纠正地址、撤回取消。
- 退款售后：退款原因缺失、完整退款、多轮原因补充、退款进度、超可退金额、换货与退款区分。
- 商品咨询：依据资料作答、资料不足、商品不明确、资料冲突、实时库存、跨轮颜色变更。
- 优惠支付：规则引用、优惠券不可用、疑似重复扣款、满减计算、叠加条件不足、依赖支付状态的取消请求。
- 异常升级：主动转人工、重复投诉、用户要求伪造退款成功、服务超时、多意图、订单号冲突。

对应4.3.1意图、4.3.2槽位、4.3.3澄清、4.3.4状态、4.3.5异常与人工升级。另含少量4.1式有据回答，服务于客服资料查询。

## 输入与输出约定

messages包含system、user、assistant；多轮样本保留完整历史。user.content是应用封装的JSON字符串：

```json
{"user_text":"帮我查订单DEMO202610240001到哪了。","context":{}}
```

context是演示应用注入的查询结果或业务资料，不能由终端用户自由填写。在真实应用中必须由可信业务服务构造、校验并与对应用户权限绑定；对用户提交的原文只能作为user_text处理。资料中的references使用局部来源编号，编号仅在当前样例内有效。

assistant.content是结构化JSON字符串，结构如下：

```json
{
  "intents":["query_logistics"],
  "slots":{"order_id":"DEMO202610240001"},
  "missing_slots":[],
  "next_action":"query_order",
  "reply":"我先查询这笔订单的物流记录，具体进度以查询结果为准。",
  "handoff_summary":null,
  "evidence_ids":[]
}
```

- `intents`：有序意图列表，多意图优先处理前置查询。不是概率分数。
- `slots`：已给出的信息。订单号为字符串；金额为两位小数字符串；歧义订单只记录`candidate_order_ids`。
- `missing_slots`：当前推进必需但缺失、无效或待重新确认的字段。例如超可退金额时，虽然有原始`requested_amount`，仍需重新确认合法金额。并非所有后续字段一次性索取。
- `next_action`：建议下一动作，由应用执行，不是工具调用已完成的证明。
- `reply`：直接展示给用户的自然语言。前端通常只展示此字段，不展示整段JSON。
- `handoff_summary`：仅转人工时填写，汇总已知问题及未完成步骤。
- `evidence_ids`：支持回复的资料编号；必须存在于本条输入的context.references中。

意图标签、动作枚举及其具体用法以样本与生成脚本为准。查询使用query_order/query_refund/query_product；澄清使用clarify；执行前确认使用confirm_action；核验使用check_*；转人工使用handoff；撤回或拒绝伪造结果使用no_action。预留的request_*表示将来流程引擎可处理的提交动作，本版并不覆盖每个预留动作。

训练时对assistant回复计算损失，system和user输入应被屏蔽；是否对历史assistant回复计算损失，按框架训练目标配置。按所用模型的聊天模板编码，核对截断长度能容纳系统提示、多轮历史和完整目标。这里没有绑定某个模型或训练框架，也未执行实际微调。

## 数据隔离与评估

每类前4个场景族进入训练，第5个进入验证，第6个进入测试，再在各集合内部固定种子打乱。同一场景族的5条变体始终在同一集合。这样可避免同一模板仅更换订单号后跨集合；但共享输出模式与系统提示仍使此测试集不能代替独立真实业务评估。

建议分别评估：意图集合匹配率、槽位精确率/召回率、next_action准确率、澄清字段正确率、引用有效率、JSON可解析率；对回复的事实依据、错误承诺、多轮信息保留和人工升级进行人工抽检。不要只用文本完全一致率衡量自然语言回复，也不要只报告格式检查通过。

## 复现

在本项目工作目录执行：

```powershell
.\.venv\Scripts\python.exe .\data\ecommerce_sft_v1\build_dataset.py
.\.venv\Scripts\python.exe .\data\ecommerce_sft_v1\validate_dataset.py
```

构建会覆盖本数据目录中的同名生成文件。代码只依赖Python标准库；不会自动安装依赖或启动训练。校验通过表示数据结构及所列规则满足要求，不代表标签已由业务专家批准或模型效果达到验收标准。
